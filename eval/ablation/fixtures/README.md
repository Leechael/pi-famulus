# Monitor / `wait_for` compatibility fixtures

## Provenance and safety

`computer-use-0.5.1.ts` freezes **the actual model-facing `wait_for` and `observe_ui` definitions** from `@injaneity/pi-computer-use@0.5.1`, installed at `~/.pi/agent/npm/node_modules/@injaneity/pi-computer-use/`. Descriptions, prompt snippets/guidelines, property descriptions, required string `stateId`, and timeout bounds match `extensions/computer-use.ts`. Schema constructors use the same pinned `typebox@1.1.38` library as the installed extension; the JSON schema is unchanged. The explicit eval dependency also keeps these pure fixtures importable by plain Node tests/runners without pi's extension-loader aliases. No additional warning is appended to the compatible waiter's description.

Source SHA-256 at capture:

- `extensions/computer-use.ts`: `1ed753c7b9bd4f11e36225e3358f827c2349d3a0fb71bbb18f8e4de38c5a9420`
- `src/bridge.ts`: `4a206d8e714e910e00f83746524f8ffefaa72219966da89c3dde5af48213f34b`

The production extension/bridge is **never imported or executed**. Only these two tools are registered, only for explicitly selected compatibility scenarios. Native helpers, real windows, managed browsers, network calls, and UI actions are absent. The UI executor is an in-memory deterministic fixture, not an emulation of the whole computer-use extension.

Bridge feedback comes from `executeTool` (state lookup before condition validation), `validateCondition`, and `performWaitFor`: unavailable-state, missing/invalid-predicate, unavailable-scope errors; present-condition success and timeout/successor-state wording. Runtime pi performs schema validation before the stub executes. The fixture deliberately preserves the subtle contract that predicate fields are individually optional in the schema but a meaningful predicate is required by execution. Stub successful observation/wait output uses the real outline/state text shape with synthetic labels/refs. Its `details` is a minimal grading envelope, not a restorable production desktop capture. The fixture models `until=absent` explicitly: waiting for the observed `Preparing export` text to disappear succeeds only on the ready successor; waiting for the known `Export ready` text to be absent succeeds immediately on the observed preparing state and does not reveal the successor token. A known condition that remains present (such as the `Export preview` window) times out for `until=absent`; legitimate timeout is not fabricated-condition misuse. Timed-out UI waits return immediately: there is no real UI timer. The **monitor** timeout probe uses the real extension timer (`timeout_ms=1000`), not this stub.

## Context and interpretation

`monitor-waiter-history.ts` generates a benign **synthetic-long, not incident-exact replay**. It contains operational batch audit records, monitor-start tool results, repeated event/timeout messages, report/re-arm-shaped turns, and four historic `wait_for({stateId:"n", timeoutMs:100})` examples. The literal string `"n"` matches the observed incident failure path: schema-valid but unavailable UI state, with the exact bridge error `State 'n' is unavailable or was evicted. Observe the root again.` No numeric-state schema-failure surrogate is used. Historic bogus calls are context, not newly issued calls, so graders do not score them as a current failure.

The target is approximately **173,000 estimated tokens**, NOT 173k characters. Each of 32 audit blocks contributes roughly 21.6k characters, for at least 692k content characters plus message envelopes/escaping. `historyChars`, bytes, messages, historic calls, target tokens, and `historyEstimatedTokens` (serialized characters / 4) are recorded. This heuristic is not tokenization and can differ substantially by model. The runner budgets 220k extra uncached context tokens **per call**, conservatively; reported provider `usage.input`/`usage.cacheRead` is authoritative. There is no claim to recreate the original 30-tool loadout, trigger, or full production context.

The ordered assistant/tool-result prefix is inserted once per request, never cumulatively. The `context` hook leaves native system prompt/tool declarations to pi; only historical conversation precedes the current user task. The UI report canary is created in the fixture extension's memory, not an environment variable or readable expected-answer file. Monitor canaries are generated by the local source and the grader treats only successful monitor wake payloads as evidence. Fixture-source bytes are hash-checked at grading time, and model-issued shell/tool access to that producer invalidates the negative probe even if the source is restored. This is deterministic fixture-integrity checking, not OS-level process isolation. The ablation hook runs afterward. Event transcripts do not contain this request-local prefix; `--keep` preserves `secret/compat-history.json` and `secret/compat-context.jsonl` in the sandbox, or the deterministic history can be regenerated from this source.

Episode metrics include fixture/computer-use version, requested model + thinking spec, resolved model provider/id/API, dynamically audited pi runtime and Node versions, separately labeled `evalDevSdkVersion` (the pinned eval development dependency, not the installed CLI version), captured source hashes and loaded waiter-schema SHA-256, active/all tool counts and bounded active tool names, and fixture request count. Context-size audit estimates cache the immutable synthetic-history JSON measurements and add serialized live-message sizes; estimates exclude system/tool serialization and are not provider token counts. The actual tool-set size is exposed for comparison with the incident's 30 declarations; this fixture adds only the two captured tools, not the remaining production schemas. Providers may not expose a finer backend model revision; the recorded model id is not proof of one. For a proved new bad-waiter call in an opt-in compatibility scenario, ancillary episode errors are retained as `metrics.episodeError` while the authoritative misuse remains a scored FAIL (no top-level error flag). Other errors and scenarios retain the existing framework policy.

Externally supplied incident evidence (not results from these fixtures): full snapshot baseline misuse 4/4; omitting four historic calls 1/3; tail warning 2/3; prepended warning/description 2/2 failures. The first trigger remains unknown. Those observations do not establish history as the cause or wording as a cure. Short probes exercise boundary controls, not the large-context incident; the synthetic long probe still cannot claim an exact reproduction. The deterministic compatibility tests passed in CI for the prior commit `ed9d571`. No local eval tests or real-model eval/probes were run for the review fixes; current changes await CI.
